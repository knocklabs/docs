This tutorial is for content and product teams that create and update notifications in Knock. It assumes your engineering team has already configured the regional accounts and the [sync described in this tutorial set](/tutorials/multiple-regions/overview#how-changes-reach-each-region).

You'll learn where to make changes, how approved changes reach each region, and how to handle content that needs to differ between regions.

## Where to make changes

Make every change to shared content in the **main account's [development environment](/version-control/environments)**. Don't edit shared content in a regional account or directly in the main account's staging or production environments.

- **Edits in a regional account are overwritten.** The sync replaces shared resources in each region with the main account's version, so an edit made in a region disappears the next time that resource syncs.
- **Changes made directly in staging bypass the sync.** The sync reacts when the main account [promotes](/version-control/commits#promoting-commits) changes into staging. Creating or editing a resource directly in staging doesn't produce that promote, so the change doesn't follow the regional sync.

Each region has its own dashboard and sign-in, so your main account and a regional account may be in different regions. To check where you are, look at the dashboard's URL, which shows the region you're signed in to, and the account and environment names at the top of the sidebar. If you can't find your main account in the account switcher, it's in a different region, and you'll need to sign in to that region's dashboard.

As part of [planning your account structure](/tutorials/multiple-regions/overview#plan-your-account-structure), we recommend tagging shared resources with a tag such as `shared` and region-only resources with a tag such as `eu-only`. Your team can then build views in each regional account that hide shared resources by default, making it easier to find the resources you can edit there.

Region-only resources are the exception to the main-account rule. Create and edit a resource directly in a regional account when it should exist only in that region. Consider using a region prefix in its key, such as `eu-welcome-email`, and a tag such as `eu-only` to distinguish it from shared resources.

These rules also apply when you use the [Knock MCP server](/ai/mcp-server) or another AI tool. Point the tool at the main account's development environment for shared content, and use it in a regional account only for region-only resources.

## The lifecycle of a change

The [overview explains the full regional model](/tutorials/multiple-regions/overview#how-changes-reach-each-region). For day-to-day content work, a shared change moves through four stages:

1. **Edit.** Make your change in the main account's development environment.
2. **Commit.** [Commit](/version-control/commits) the change when it's ready for review.
3. **Promote to staging.** [Promoting](/version-control/commits#promoting-commits) to the main account's staging environment is the approval point. It tells the sync your change is approved, and the sync applies it to every region's staging environment.
4. **Promote to production.** Promote the main account's staging environment to production. The sync promotes every region to production too. If your team ships notification changes with your application deploys instead, your engineering team's deploy pipeline does this step.

If you work in [branches](/version-control/branches), merging a branch lands its changes in the main account's development environment. They still need a promote to staging to reach the regions.

After a change syncs, you'll see a matching commit in each regional account, made by a service token rather than a person.

To verify a change, open the resource in the regional account's staging environment and confirm that it matches the main account. You may need to sign in to that region's dashboard separately. After the production promote, check the resource in each account's production environment the same way.

There are two exceptions to this lifecycle.

### Message types go live right away

[Message types](/in-app-ui/message-types/overview) are shared across every environment in an account and can't be promoted. When you commit a message type in the main account, it goes live right away in every environment of every account, including production. There's no staging step.

Check with your engineering team before changing a message type that live [guides](/concepts/guides) use. Adding a field is safe, but renaming or removing one can break guides that are already live.

### Archives take effect right away

Archiving a shared resource in the main account removes it from every environment of that account right away, including production. There's no staging step, and the archive isn't synced: your team [should set up alerting](/tutorials/multiple-regions/syncing-accounts#archives) to be notified when a shared resource is archived to then take the necessary next steps for the regional accounts.

Archive only what's no longer used anywhere, including by region-only resources. Never archive a shared resource from a regional account.

## Before you promote

A promote can include more than the change you just made. Before every promote, review all unpromoted commits for the resources you're promoting. This includes earlier commits to the same resource, including changes from another team member. Review them on the **Commits** page in your main account.

Then check the dependencies that apply to your change:

- **A workflow uses a new or updated reusable request.** Promote the reusable request with the workflow so it exists in each regional account before the workflow syncs.
- **A guide uses a new or updated message type.** Commit the message type before promoting the guide. Message types sync when they're committed rather than when they're promoted.

## Handling content differences

Use shared content when every region can use the same resource. When content needs to vary by region, use the table below to choose whether to change a value inside the shared resource or create a separate resource for that region.

| The difference                                      | Use                                                                               | Where to configure it                                                               |
| --------------------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| The content is the same everywhere                  | A shared resource                                                                 | Edit it in the main account's development environment                               |
| A small value, such as a footer link or support URL | A [variable](/concepts/variables) with a value for each region                    | Create the same variable key and set its value in each account                      |
| Content depends on recipient data                   | [Conditions](/concepts/conditions) in the template                                | Add the conditions to the shared resource in the main account                       |
| The content is entirely different                   | A region-only resource                                                            | Create and edit it in that regional account's development environment               |
| Language                                            | [Translations](/template-editor/translations), synced like other shared resources | Create translations in the main account, and set the default locale in each account |

Use conditions when the shared template can choose content from recipient data that is already available in that region, such as a recipient's country or plan. The resource remains shared; only the rendered content changes.

## Changes to make in each account

Some resources and actions aren't handled by the content sync. A team member with the required permissions must make these changes in each account:

- Create or update a variable, channel, channel group, or source.
- Archive a shared resource in each regional account after it is archived in the main account.
- Check whether any region-only resource still depends on a shared resource before archiving it.
- Ask the team that operates the sync to investigate a change that didn't reach a region.

## Frequently asked questions

<AccordionGroup>
  <Accordion
    title="Why did my edit in a regional account disappear?"
    anchorSlug="faq-regional-edit-disappeared"
  >
    The resource is shared, so the next sync replaced it with the main account's
    version. Make the change in the main account's development environment, or,
    if it should only apply in one region, use a [variable or a region-only
    resource](#handling-content-differences).
  </Accordion>
  <Accordion
    title="Why hasn't my change shown up in a region yet?"
    anchorSlug="faq-change-not-in-region"
  >
    Changes reach the regions when they're promoted to the main account's
    staging environment, so check that your change has been committed and
    promoted. If it was promoted and still hasn't arrived, the sync may have
    failed. Ask the team that operates the sync to re-run it.
  </Accordion>
  <Accordion
    title="Why did my message type change go live in production right away?"
    anchorSlug="faq-message-type-live-in-production"
  >
    Message types are shared across every environment and can't be promoted, so
    committing one makes it live everywhere at once. See [message types go live
    right away](#message-types-go-live-right-away).
  </Accordion>
  <Accordion
    title="I archived something in the main account. Why is it still in a region?"
    anchorSlug="faq-archive-still-in-region"
  >
    Archives aren't synced. Your team receives an alert, and a member with the
    required permissions archives the resource in each regional account.
  </Accordion>
  <Accordion
    title="Can I make one small change for just one region?"
    anchorSlug="faq-change-for-one-region"
  >
    Yes. For a small value, such as a link, use a variable with a different
    value in each region. A team member with the required permissions can
    configure the variable in each account. For entirely different content,
    create a region-only resource in that region. See [handling content
    differences](#handling-content-differences).
  </Accordion>
  <Accordion
    title="Who promotes changes to production?"
    anchorSlug="faq-who-promotes-to-production"
  >
    Anyone who can promote in the main account's staging environment. When they
    promote to production, the sync promotes every region to production too. If
    your team ships notification changes with your application deploys instead,
    your deploy pipeline promotes every account.
  </Accordion>
</AccordionGroup>

Knock supports data residency, so you can keep your customer and notification data in a specific region. Each Knock account is hosted in a single region, which you choose when you create the account.

If you serve customers in more than one region and need each region's data to stay in that region, you run a separate Knock account in each one. We call these regional accounts. Regional accounts are independent, and Knock doesn't share data or configuration between them. These tutorials cover how to keep your notifications consistent across your regional accounts.

The model in these tutorials moves changes through environments, so each of your accounts needs [environments enabled](/version-control/environments#enable-environments).

## How regional accounts work

With data residency, Knock stores and processes your customer and notification data in the region your account is hosted in. An account's region is set when the account is created, and an account can't be moved to a different region later.

Each regional account has its own environments, channels, API keys, members, and data. Each region also has its own dashboard and API hostnames, so your application and client-side SDKs connect to the hostnames for the region they send data to.

To keep your accounts consistent, pick one of them as your **main account**. Your team creates resources such as workflows and templates once in the main account, and a sync copies approved changes into your other regional accounts. These are your **shared resources**. See [shared and per-account resources](#shared-and-per-account-resources) for the full list. The sync moves notification **configuration** like this. It never moves end-user data. Recipients, messages, preferences, and logs stay in the account, and the region, where they were created.

## How changes reach each region

A change to a shared resource moves through four steps:

1. **Make the change in the main account.** Your team creates and edits shared resources in the main account's development environment.
2. **Promote it to staging.** [Promoting](/version-control/commits#promoting-commits) a change to the main account's staging environment is the approval point. It means "this is approved, sync it to the regions," so the regions only change when someone promotes, not every time someone saves or commits.
3. **The sync applies it to each region.** A sync job you run picks up each promote and applies the same change to every regional account's staging environment.
4. **Promote to production.** When someone promotes the main account to production, the sync promotes every region to production too.

Because staging is the approval point, a change has to be committed and reviewed in the main account before it can reach any region. A few resources reach the regions differently, such as message types. See [shared and per-account resources](#shared-and-per-account-resources) for how each one is handled.

[Syncing accounts across regions](/tutorials/multiple-regions/syncing-accounts) covers how to build the sync, and [Managing content across regions](/tutorials/multiple-regions/managing-content) covers how your team makes changes day to day.

## Shared and per-account resources

### Shared resources

If you follow the pattern in these tutorials, these resources are created once in your main account and synced to every region:

| Resource                                                                          | How it reaches each region                                                                                                     |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| [Workflows](/concepts/workflows)                                                  | Synced when promoted to staging                                                                                                |
| [Email layouts](/integrations/email/layouts)                                      | Synced when promoted to staging                                                                                                |
| [Partials](/template-editor/partials/overview)                                    | Synced when promoted to staging                                                                                                |
| [Translations](/template-editor/translations)                                     | Synced when promoted to staging                                                                                                |
| [Guides](/concepts/guides)                                                        | Synced when promoted to staging                                                                                                |
| [Audiences](/concepts/audiences)                                                  | Synced when promoted to staging                                                                                                |
| [Reusable requests](/designing-workflows/fetch-function#reusable-fetch-functions) | Synced when promoted to staging                                                                                                |
| [Message types](/in-app-ui/message-types/overview)                                | Synced when committed. Message types can't be promoted, so a committed change reaches every environment, including production. |

The sync copies each resource's content. It doesn't carry the following, so set them in each region:

- **Guide active status.** Activate each guide in each region. Pushing a guide doesn't set its status.
- **Guide priority order.** Set the order in each region. Priority order is managed only in the dashboard.
- **Static audience members.** Add members to static audiences in each region. Dynamic audiences compute their members from the region's own users.
- **Archives.** Archiving a shared resource in the main account takes effect in all of its environments right away, but isn't synced. Archive it in each region after the sync alerts you.

### Resources set up in each account

These hold region-specific values or credentials, so you create them in each account:

| Resource                                                         | How to set it up in each region                                                                                                            |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| [Channels](/concepts/channels)                                   | Create each channel with the same key as in the main account, using the region's credentials. Synced workflows find their channels by key. |
| [Channel groups](/integrations/overview#channel-groups)          | Create them with the same keys as in the main account.                                                                                     |
| [Variables](/concepts/variables)                                 | Create each one with the same key and a region-specific value.                                                                             |
| [Sources](/integrations/sources/overview)                        | Recreate each source and its event mappings, set its signing secret, and point the sending system at the region's source URL.              |
| [Broadcasts](/concepts/broadcasts)                               | Create them in each account.                                                                                                               |
| [Outbound webhooks](/developer-tools/outbound-webhooks/overview) | Create them in each account. Each webhook has its own signing secret.                                                                      |
| [Extensions](/integrations/extensions/overview)                  | Set up each extension, including any data exports, in each account.                                                                        |
| [API keys](/developer-tools/api-keys)                            | Each environment comes with its own API keys.                                                                                              |
| [Service tokens](/developer-tools/service-tokens)                | Generate a service token in each account for the sync to use.                                                                              |

Also configure these settings in each account:

- **[Preference settings](/preferences/overview).** Set up your default preferences and preference center.
- **[Branding](/template-editor/branding).** Set your logo, icon, and brand colors.
- **[Default locale](/template-editor/translations#get-started).** If using translations, be sure to set the default `locale` in each account.

## Setting up your accounts

The sync depends on every account looking the same from the outside. Make these decisions before you create your first regional account.

- **Main account.** Choose the account your team will build in. Shared resources are created and edited only there.
- **Environments.** We recommend at least a development and a production environment. These tutorials use three: development, staging, and production. Use the same environments, in the same order, in every account, since the sync pushes to each region's development environment and promotes from there.
- **Keys.** Shared resources use identical keys in every account. Give region-only resources a unique prefix, such as `eu-welcome-email`, so they never collide with a shared key.
- **Regional differences.** Put small differences, such as a support URL or footer link, in variables, and create entirely different content as a region-only resource. See [handling content differences](/tutorials/multiple-regions/managing-content#handling-content-differences).
- **Tags and views.** Tag shared resources (for example, `shared`) and region-only resources (for example, `eu-only`), then build views in each regional account that hide shared resources by default. Tags and views are available on workflows, partials, guides, and broadcasts.

## Team access

Each regional account has its own members, roles, and authentication settings. Plan who needs access to which accounts, and what they can do in each.

- **Signing in.** Each region has its own dashboard and sign-in, and the account switcher only shows accounts in the region you're signed in to. Anyone who works in more than one region signs in to each one separately. {/* TODO: Confirm with eng (friction log question 3). */}
- **SSO and SCIM.** [SAML SSO](/manage-your-account/saml-sso) and [directory sync](/manage-your-account/directory-sync) are configured per account. {/* TODO: Confirm how multiple accounts on one email domain work with SSO and SCIM before publishing. */}
- **Roles.** Use [custom permission groups](/manage-your-account/roles-and-permissions#custom-permission-groups) to limit who can edit content in each region. Shared resources in a regional account are overwritten by the next sync, so most of your team only needs to view them there.
- **Customer data obfuscation.** [Customer data obfuscation](/manage-your-account/roles-and-permissions#customer-data-obfuscation) can differ per account. For example, your US team might have full access in the US account and see obfuscated data in the EU account.

## Next steps

Before you build anything:

1. Pick your main account.
2. Enable environments in every account, and match their names and order.
3. List what each region needs from the [per-account resources and settings](#resources-set-up-in-each-account).
4. Move regional differences into variables, and choose a prefix and tags for region-only resources.
5. Plan who needs access to each account.

Then continue with the tutorial for your role:

- **Engineering.** Set up the sync with [Syncing accounts across regions](/tutorials/multiple-regions/syncing-accounts).
- **Content and product teams.** Learn where and how to make changes with [Managing content across regions](/tutorials/multiple-regions/managing-content).

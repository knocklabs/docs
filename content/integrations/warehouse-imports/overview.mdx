Warehouse imports read a table or SQL query in your data warehouse on a schedule and write the rows into Knock. Use them to keep recipient data in Knock up to date from the warehouse you already maintain, without building a sync job or using a reverse ETL tool.

## How warehouse imports work

Setting up an import takes two steps:

1. **Connect a warehouse.** A warehouse is one connection to one database in Amazon Redshift or Snowflake. You add it once under **Settings** > **Integrations** > **Extensions** > **Warehouses**, and every environment in your account can import from it. See [connecting a warehouse](/integrations/warehouse-imports/connecting-a-warehouse).
2. **Create an import.** An import belongs to one environment. It names the warehouse, the table or SQL query to read, the column that identifies each row, how columns map to Knock fields, and how often to sync. See [creating an import](/integrations/warehouse-imports/creating-an-import).

Once an import is published, Knock reads the source on its schedule, finds the rows that changed since the last sync, and applies them in Knock. Each sync is listed on the import's **Runs** tab with how many rows were read, applied, and rejected. See [managing imports](/integrations/warehouse-imports/managing-imports).

## Supported warehouses

| Warehouse       | Authentication                                                       |
| --------------- | -------------------------------------------------------------------- |
| Amazon Redshift | An IAM role Knock assumes, optionally through an SSH tunnel          |
| Snowflake       | Key-pair authentication with a key Knock generates or one you supply |

Knock never stores a database password for either warehouse.

## What you can import

Each import writes to one target, chosen when you create it:

| Target           | What each row does                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Users            | Creates or updates a [user](/concepts/users). The primary key becomes the user's ID.                                     |
| Tenants          | Creates or updates a [tenant](/concepts/tenants). The primary key becomes the tenant's ID.                               |
| Objects          | Creates or updates an [object](/concepts/objects) in the collection you choose. The primary key becomes the object's ID. |
| Audience members | Adds a user, optionally for a tenant, to a static [audience](/concepts/audiences).                                       |

Imports only add and update data in Knock:

- A column you don't map is never changed on existing records.
- A row that disappears from the source, or a row your deleted flag column marks as deleted, leaves the record in Knock as it is.
- Audience imports add members but don't remove them.
- Tenant imports set the tenant's name and custom properties. They don't set tenant settings such as branding or preference sets.

## Environments

Warehouses are shared by every environment in your account. Imports belong to one environment, so you can import into Development and Production separately from the same warehouse.

Imports aren't part of the commit and promote flow. You create and edit an import directly in the environment it imports into, including Production. Every save creates a new version of the import, and you choose which version is live by publishing it. Imports aren't available in branch environments.

## Permissions

| Action                                        | Built-in roles                | Custom permission group capability |
| --------------------------------------------- | ----------------------------- | ---------------------------------- |
| Add, edit, and test warehouse connections     | Owner, Admin                  | Integrations: manage               |
| View warehouses and imports                   | Owner, Admin, Member, Support | Recipient data: view               |
| Create, edit, publish, run, and pause imports | Owner, Admin, Member          | Recipient data: manage             |

Recipient data is an environment capability, so a custom permission group can manage imports in Development but only view them in Production. See [roles and permissions](/manage-your-account/roles-and-permissions).

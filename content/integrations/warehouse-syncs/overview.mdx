Warehouse syncs read a table or SQL query in your data warehouse on a schedule and write the rows into Knock. Use them to keep recipient data in Knock up to date from the warehouse you already maintain, without building a sync job or using a reverse ETL tool.

Warehouse syncs bring data from your warehouse into Knock. To send Knock's notification data to your warehouse instead, see [data warehouse sync](/integrations/extensions/data-sync).

## How warehouse syncs work

Setting up a sync takes two steps:

1. **Connect a warehouse.** A warehouse is a [source](/integrations/sources/overview) that connects to one database in Amazon Redshift or Snowflake. You add it once from **Platform** > **Sources**, and every environment in your account can sync from it. See [connecting a warehouse](/integrations/warehouse-syncs/connecting-a-warehouse).
2. **Create a sync.** A sync belongs to one environment. It names the table or SQL query to read, the column that identifies each row, how columns map to Knock fields, and how often to run. See [creating a sync](/integrations/warehouse-syncs/creating-a-sync).

Once a sync is published, Knock reads the source on its schedule, finds the rows that changed since the last run, and applies them in Knock. Each run is listed on the sync's **Runs** tab with how many rows were read, applied, and rejected. See [managing syncs](/integrations/warehouse-syncs/managing-syncs).

## Supported warehouses

| Warehouse       | Authentication                                                       |
| --------------- | -------------------------------------------------------------------- |
| Amazon Redshift | An IAM role Knock assumes, optionally through an SSH tunnel          |
| Snowflake       | Key-pair authentication with a key Knock generates or one you supply |

Knock never stores a database password for either warehouse.

## What you can sync

Each sync writes to one target, chosen when you create it:

| Target           | What each row does                                                                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Users            | Creates or updates a [user](/concepts/users). The primary key becomes the user's ID.                                                                  |
| Tenants          | Creates or updates a [tenant](/concepts/tenants). The primary key becomes the tenant's ID.                                                            |
| Objects          | Creates or updates an [object](/concepts/objects) in the collection you choose. The primary key becomes the object's ID.                              |
| Audience members | Adds a user, optionally for a tenant, to a static [audience](/concepts/audiences).                                                                    |
| Subscriptions    | [Subscribes](/concepts/subscriptions) a user to an object in the collection you choose. Knock creates the user or the object if it doesn't exist yet. |

A column you don't map is never changed on existing records. Tenant syncs set the tenant's name and custom properties. They don't set tenant settings such as branding or preference sets.

## Removed and deleted rows

A row is deleted when it disappears from the source or when your [deleted flag column](/integrations/warehouse-syncs/creating-a-sync#5-change-detection) marks it as deleted. What Knock does with a deleted row depends on the target:

| Target                  | When a row is deleted                                                                                    |
| ----------------------- | -------------------------------------------------------------------------------------------------------- |
| Users, tenants, objects | Nothing. The record stays in Knock as it is.                                                             |
| Audience members        | Nothing. Audience syncs add members but don't remove them.                                               |
| Subscriptions           | Knock unsubscribes the user from the object, so subscriptions in Knock match the rows in your warehouse. |

## Environments

Warehouses are shared by every environment in your account. Syncs belong to one environment, so you can sync into Development and Production separately from the same warehouse.

Syncs aren't part of the commit and promote flow. You create and edit a sync directly in the environment it syncs into, including Production. Every save creates a new version of the sync, and you choose which version is live by publishing it. Each published version is listed on the sync's **Changes** tab, where you can revert to an earlier one. Syncs aren't available in branch environments.

## Permissions

| Action                                              | Built-in roles                | Custom permission group capability |
| --------------------------------------------------- | ----------------------------- | ---------------------------------- |
| Add, edit, and test warehouse connections           | Owner, Admin                  | Integrations: manage               |
| View warehouses and syncs                           | Owner, Admin, Member, Support | Recipient data: view               |
| Create, edit, publish, run, pause, and revert syncs | Owner, Admin, Member          | Recipient data: manage             |

Recipient data is an environment capability, so a custom permission group can manage syncs in Development but only view them in Production. See [roles and permissions](/manage-your-account/roles-and-permissions).
